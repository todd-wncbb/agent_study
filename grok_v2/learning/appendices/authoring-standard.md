# 写作与证据规范

本规范用于让几十篇文章保持相同的深度、术语和可验证性。

## 核心原则

### 1. 解释连接，不翻译代码

读者最需要的是边界、状态、因果和生命周期。代码片段只在以下情况下使用：

- 展示公开 API 或关键数据结构；
- 说明控制流中容易误解的分支；
- 解释 Rust 所有权或并发约束；
- 给出可以直接运行的最小实验。

不得用连续粘贴源码代替解释。

### 2. 结论必须可回到证据

核心结论至少绑定一种证据：

- `Cargo.toml` 中的依赖或 feature；
- `lib.rs` / `mod.rs` 暴露的模块边界；
- 类型、trait、函数或常量；
- 调用点；
- 测试或 fixture；
- 实际运行输出。

引用格式优先使用：

```text
crates/codegen/xai-grok-agent/src/lib.rs
符号：Agent、AgentBuilder、AgentDefinition
```

行号只用于逐代码 walkthrough。普通架构文章使用符号名，降低代码移动造成的维护成本。

### 3. 区分四种陈述

- **源码事实**：源码直接表达的事实。
- **阅读模型**：为了学习而压缩出的概念层。
- **设计推断**：从实现推测的目的，必须使用“可以看作”“说明”“推测”等措辞。
- **学习建议**：优先级、练习或跳读建议。

不能把设计推断写成作者明确意图。

### 4. 同时覆盖顺利和不顺利的路径

运行链路不能只写 happy path。至少检查：

- 初始化失败；
- 用户取消；
- channel 关闭；
- 超时与重试；
- 权限拒绝；
- 序列化或协议错误；
- 进程中断与恢复。

## 核心文章模板

```markdown
# 主题

## 这篇解决什么问题
## 先建立心智模型
## 范围与非目标
## 相关 crate 和源码入口
## 核心类型与不变量
## 正常执行流程
## 状态与所有权
## 并发、任务和 channel
## 错误、取消与恢复
## 安全边界
## 时序图
## 一次真实代码追踪
## 如何运行或验证
## 常见误解
## 修改影响
## 本篇术语表
## 自测题
## 源码依据
```

不是每篇都必须机械保留所有小节，但删减时不能丢掉该主题的关键风险。例如纯数据类型 crate 可以不写并发；权限主题不能删安全边界。

## 术语表规则

每篇文章必须包含“本篇术语表”，不能只依赖全局术语表。原因是同一个词在不同上下文中可能含义不同，例如 `runtime` 既可能指 Tokio 的异步执行环境，也可能泛指 agent 的整套运行逻辑。

术语表至少覆盖：

1. 本篇第一次出现的缩写；
2. 没有直接中文对应的工程词；
3. 在本项目中含义比日常含义更窄的词；
4. 容易与相似概念混淆的词；
5. 图中使用但正文没有充分解释的词。

推荐格式：

```markdown
| 名词 | 白话解释 | 在本篇中的具体含义 |
| --- | --- | --- |
| LocalSet | 只在当前线程调度一组异步任务的 Tokio 容器 | stdio agent 用它运行不要求 `Send` 的本地任务 |
```

解释应先用白话说明“它是干什么的”，再说明“此处对应哪段代码”。禁止使用另一个未解释的术语循环定义。例如不能只写“IoC hook 是一个 DI seam”。

## 图示规范

- 分层关系使用 flowchart。
- 消息先后和异步交互使用 sequence diagram。
- 生命周期使用 state diagram。
- crate 数量过多时分组，不画不可阅读的“毛线团”。
- 每个图节点必须能落到一个源码模块、类型、进程或明确的阅读模型。
- 图后用文字指出哪些边界是真实 API，哪些只是教学分组。

## 术语规范

- crate 保留 Rust 原词，第一次出现时解释为“编译单元/包”。
- `session`、`turn`、`sampling iteration`、`tool call` 不随意互换。
- ACP 指宿主/编辑器与 agent 的协议边界；MCP 指 agent 与外部工具服务的协议边界。
- “任务”必须注明是 Tokio task、用户任务、Subagent task 还是 workflow task。
- “状态”必须尽量说明拥有者，避免只写“系统保存”。

## 本篇术语表

| 名词 | 白话解释 | 在本篇中的具体含义 |
| --- | --- | --- |
| manifest | 描述一个软件包怎样构建的清单文件 | Rust crate 的 `Cargo.toml` |
| public API | 其他模块或 crate 被允许依赖的公开接口 | `pub` 类型、trait、函数及其约定，不等于所有内部实现 |
| feature | 编译时选择性开启的一组代码或依赖 | Cargo feature，常通过 `#[cfg(feature = "...")]` 控制 |
| fixture | 为测试预先准备的数据或环境 | 示例配置、临时 workspace、录制的协议消息等 |
| snapshot test | 把本次输出与已保存标准结果比较的测试 | 常用于复杂 UI、文本或序列化结果的回归检测 |
| happy path | 一切按预期成功的正常路径 | 文档还必须覆盖错误、拒绝、取消和恢复路径 |
| 不变量 | 程序运行过程中必须始终成立的条件 | 例如事件顺序、权限不能越权、一个状态只有一个有效拥有者 |
| 序列化 | 把内存对象转成可传输或可保存的数据 | 常见目标格式包括 JSON、TOML 和协议消息 |

## 完成定义

一篇核心文档完成，意味着：

1. 读者知道从哪个入口开始查源码。
2. 读者能说出核心状态由谁拥有。
3. 正常路径和至少一个失败路径得到解释。
4. 关键结论有源码证据。
5. 内部链接有效。
6. 至少有三个能够检验理解的问题。
7. 在文档基线版本上重新搜索过所有关键符号。
8. 本篇出现的陌生缩写和工程术语已经在本篇术语表解释。
